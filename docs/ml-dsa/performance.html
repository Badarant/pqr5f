Reading the figure

The stack advantage is not where you would guess. For key generation the reference and the speed-optimised port need the same stack to within 236 bytes; the port only runs faster. The gap opens at verification, where the port needs a quarter of the reference's stack, and the low-stack variant a thirty-second of it.

ROM is what pays for it. Roughly twice the reference, consistently: 1.86× for a key-generation image, 2.28× for a signing one, and 2.01× for one carrying all three. Those ratios barely move across the parameter sets, which is what an unrolled loop and a twiddle table cost against C that computes them.

Two near-collisions in the panels are real. ML-DSA-44's reference sits almost on top of ML-DSA-65's speed-optimised port, and ML-DSA-65's reference on ML-DSA-87's. Porting a larger parameter set costs about what the C reference of the next one down costs.

Not for production. These are benchmark figures. No side-channel claim is made beyond one measurement of the core's multiplier, signing time depends on secret values through its rejection-sampling loop, nothing here is masked or hardened against fault injection, and passing NIST's vectors is a self-check rather than a validation.

Sources. Cycles and stack from measurements.csv, ROM from codesize.csv. Stack is measured by painting it and scanning afterwards; no implementation here defines any .data or .bss, so that figure is the whole RAM budget in all nine cases. The reference is built for the same core with the same flags and gets its whole implementation in ATCM, which is the more favourable placement of the two — the ported variants keep only their assembly and Keccak there.
